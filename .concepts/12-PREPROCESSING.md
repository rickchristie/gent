# How production RAG systems preprocess documents before chunking

**Markdown has emerged as the de facto intermediate format for document preprocessing in 2024–2025 RAG pipelines**, with tools like IBM's Docling, Marker, and PyMuPDF4LLM converging on a shared pattern: convert any source format to Markdown, then chunk with structure awareness for embedding. The main alternative paradigm—Unstructured.io's typed-element JSON approach—offers superior granularity for complex documents but has not displaced Markdown's dominance. Across frontier AI labs and production frameworks, the canonical pipeline is now **Source → Markdown (or structured elements) → Structure-aware chunking → Contextual enrichment → Embedding**. Anthropic's contextual retrieval technique—prepending chunk-specific context generated by an LLM—delivers the single largest retrieval improvement documented to date, reducing failure rates by **35–67%**.

---

## The production pipeline: from raw documents to chunks

Every major RAG framework follows a variant of the same architecture. LlamaIndex uses a `Reader → Document → NodeParser → Node` pipeline, where readers convert files to `Document` objects containing plain text and metadata, then node parsers chunk them. LangChain follows a `DocumentLoader → Document → TextSplitter` pattern, with over 200 loaders routing by file type. Haystack uses a pipeline graph: `FileTypeRouter → Converters → DocumentCleaner → DocumentSplitter → Embedder → DocumentWriter`. All three frameworks store content as plain text internally, but the conversion step increasingly routes through Markdown.

The tool ecosystem has crystallized around a few dominant converters. **Docling** (IBM, MIT license, 20K+ GitHub stars) converts PDF, DOCX, PPTX, XLSX, and HTML into a unified `DoclingDocument` representation, exporting to Markdown by default. It uses the DocLayNet layout analysis model and TableFormer for table structure recognition, achieving **97.9% table cell accuracy** on sustainability report benchmarks. **Marker** (31K+ stars, GPL) produces Markdown using Surya for layout detection and OCR, with an optional LLM mode (Gemini) that yields the highest accuracy in benchmarks—**25 pages/second serial throughput on an H100**. **PyMuPDF4LLM** adds Markdown export to PyMuPDF for fast CPU-only extraction of digital PDFs, making it the speed champion at the cost of lower complex-table fidelity.

Unstructured.io takes a fundamentally different approach. Instead of converting to Markdown, it decomposes documents into typed elements—`Title`, `NarrativeText`, `ListItem`, `Table`, `Image`, `Header`, `Footer`, and others—each carrying rich metadata (page number, bounding box coordinates, parent ID, category depth). Its "Hi-Res" strategy uses YOLOX/Detectron2 for layout detection, and tables are preserved as HTML in a `text_as_html` metadata field. The `chunk_by_title` strategy groups elements under section headings, producing semantically coherent chunks. This element-based approach outperformed token-based chunking on the FinanceBench dataset for both retrieval and QA tasks.

The frontier AI labs handle preprocessing differently depending on their product surface. **OpenAI's file search** (Assistants/Responses API) is fully managed and opaque—users upload files, and OpenAI handles parsing, chunking, and embedding internally using hybrid vector + keyword search with reciprocal rank fusion. **Google's Vertex AI RAG Engine** uses Document AI Layout Parser for PDFs, which produces semantically aware chunks respecting document layout. **Cohere** focuses on the retrieval and generation layers, delegating document parsing to external tools and providing connectors that accept JSON results from any search endpoint. **Anthropic** does not offer an embedding model but published contextual retrieval as a preprocessing technique and recommends Voyage AI for embeddings.

## PDF conversion: the hardest problem in the pipeline

PDFs remain the single most challenging format. The fundamental split is between **native/digital PDFs** (containing embedded text extractable from PDF bytecode) and **scanned PDFs** (images requiring OCR). Modern tools like Docling, Marker, and Unstructured auto-detect which approach each page needs, routing digital pages to fast text extraction and scanned pages through OCR pipelines.

For **table extraction**, Markdown tables work for simple structures, but complex tables with merged cells or multi-level headers require HTML output. Docling's TableFormer model specifically handles table structure recognition. LlamaParse, a commercial cloud service from LlamaIndex, is "incredibly good at parsing PDFs with complex tables into well-structured markdown" and supports cross-page table detection. Pdfplumber offers precise control for targeted table extraction from well-structured digital PDFs, returning raw Python data structures that users convert via pandas. NVIDIA's Nemotron RAG documentation notes that "converting tables to markdown preserves row/column relationships in an LLM-native format, significantly reducing numeric hallucinations."

**Multi-column layouts** are handled through layout analysis models. Docling uses DocLayNet (trained on 80K+ annotated pages), Marker uses Surya layout detection, and PyMuPDF4LLM includes a built-in layout analysis module—all reconstruct proper reading order from multi-column pages. Pdfplumber and Tesseract lack reliable column detection.

For **images and figures**, three strategies dominate: (1) extract images and generate captions via VLMs like GPT-4V or Granite Vision, embedding the descriptions alongside text chunks; (2) extract as separate files with Markdown image references for downstream multimodal processing; (3) apply OCR to extract text from charts and diagrams. Most production pipelines use approach 1 for document understanding and approach 2 when visual fidelity matters.

The tool comparison breaks down clearly by use case:

| Tool | Best for | Output | Speed | Accuracy |
|------|----------|--------|-------|----------|
| **PyMuPDF4LLM** | Fast extraction, simple digital PDFs | Markdown | Fastest (CPU-only) | Low on complex tables |
| **Docling** | Complex reports, multi-format pipelines | Markdown, JSON, HTML | Moderate | 97.9% table cells |
| **Marker** | High-throughput batch processing | Markdown, JSON, HTML | 25 pg/s (H100) | Highest with LLM mode |
| **LlamaParse** | Complex financial/medical PDFs | Markdown, JSON | ~6s/doc (cloud) | High (commercial) |
| **Unstructured Hi-Res** | Element-level granularity | Typed elements → JSON | Slowest | 100% simple / 75% complex tables |
| **Azure Doc Intelligence** | Enterprise, custom doc types | Structured JSON | Cloud-dependent | Best for invoices |
| **Amazon Textract** | AWS-native form processing | Structured JSON | Cloud-dependent | Good for receipts/forms |

## HTML, Word, PowerPoint, and structured data

**HTML preprocessing** has converged on a clear pipeline: render with headless browser → extract main content → convert to Markdown. Jina Reader API uses Chrome + Mozilla Readability + Turndown for this pipeline, with an optional **ReaderLM-v2** (1.5B parameter SLM) for complex pages that achieves ROUGE-L of 0.84. Firecrawl auto-detects whether JavaScript rendering is needed, strips ads and navigation before conversion, and supports full-site crawling. Trafilatura achieves the highest benchmarked accuracy for main content extraction (**F1 = 0.958** on ScrapingHub benchmarks) and powers Haystack's HTML converter.

An academic counterpoint worth noting: the **HtmlRAG paper** (WWW 2025) found that cleaned HTML can outperform both plain text and Markdown for RAG when used with long-context LLMs, because HTML tags like `<code>`, `<th>`, and `<td>` carry semantic meaning lost in conversion. This approach hasn't gained production traction due to HTML's token overhead, but signals that Markdown conversion is lossy.

**Word documents** follow the pattern DOCX → Markdown via Docling (highest accuracy), mammoth → HTML → markdownify (established), or Microsoft's MarkItDown (fastest but ~47% overall success rate on mixed documents). Mammoth maps Word styles to semantic HTML elements rather than preserving visual formatting. Headers and footers are detected and optionally excluded by Docling; mammoth ignores them; python-docx provides raw access.

**PowerPoint** follows a **one-slide-per-chunk** pattern as the dominant approach. Speaker notes should be concatenated with slide body text for richer context. For image-heavy slides, LangChain's multimodal RAG template reports **90% accuracy** when using GPT-4V to summarize slide images and embed those summaries, compared to just 20% for text-only extraction. Python-pptx is the standard extraction tool, with Docling and Unstructured offering integrated pipelines.

**Structured data** (CSV, JSON, Excel) presents a fundamentally different challenge. Embedding models suffer from **semantic collapse** on tabular data—adjacent rows differ by tiny lexical changes, producing nearly identical vectors. The emerging best practice is a **hybrid approach**: store tabular data in SQL databases (DuckDB, SQLite) and use intent detection to route structured queries to deterministic SQL lookups rather than vector search. When embedding is necessary, converting rows to **natural language narration** yields a **19.1% boost in Recall@10 and 27.2% boost in MRR** compared to embedding raw JSON (measured on Amazon ESCI with all-MiniLM-L6-v2). LangChain's CSVLoader converts each row to key-value format; LlamaIndex's PagedCSVReader creates one document per row.

## Why Markdown won and where it falls short

Markdown's rise as the universal intermediate format rests on three pillars. First, **token efficiency**: Markdown uses ~67% fewer tokens than raw HTML while preserving semantic structure. Second, **chunking compatibility**: Markdown headings (`#`, `##`, `###`) provide natural semantic boundaries. LangChain's `MarkdownHeaderTextSplitter` splits on these headers and stores the heading hierarchy as metadata, enabling retrieval that understands document structure. Third, **LLM familiarity**: models are trained on vast quantities of Markdown from GitHub, documentation sites, and web content.

The evidence that Markdown helps embedding quality is suggestive but not conclusive. One benchmark found **89% retrieval accuracy** for Markdown versus 71% for plain text and 62% for raw HTML. However, embedding models tokenize Markdown syntax characters (`#`, `|`, `-`) as regular tokens—they have no special structural understanding of Markdown. The retrieval improvement likely comes from better information density and the fact that structural markers like `#` correlate with important content in training data, not from models "parsing" Markdown.

Markdown's limitations are real. It cannot represent merged table cells, multi-level headers, or complex layouts. IBM's own Granite-Docling team developed **DocTags** specifically because "general-purpose markup languages like HTML or Markdown weren't designed for image-to-sequence tasks like document conversion and have a limited vocabulary." For complex tables, **HTML** preserves more structure. For element-level granularity, **Unstructured's typed JSON** is superior. The practical synthesis: use Markdown as the default, fall back to HTML for complex tables, and consider element-based approaches for documents requiring fine-grained structural awareness.

## Tables need special treatment for embedding

Tables are where naive preprocessing fails most dramatically. Research from multiple sources converges on a key insight: **embedding models understand the topic of a table but not the spatial relationships between cells**. The Topo-RAG paper (January 2026) frames it precisely: "When we flatten a table of 50 rows and 10 columns into a single vector, we are asking the embedding model to compress 500 potential relationships into a fixed point in latent space." The TabRAG paper (NeurIPS 2025 workshop) confirms that "structured representations such as JSONs are syntactically well-defined but poorly aligned with the token distributions of pretrained foundational embedding models."

The **TARGET benchmark** (NeurIPS 2024)—the first comprehensive table retrieval benchmark—found that dense embedding retrievers significantly outperform BM25 for table retrieval, but that LLM-generated table summaries via LlamaIndex actually *lowered* retrieval performance in some cases compared to direct embedding. For text-to-SQL datasets, including data rows in the embedding lowered performance—schema-only was better.

The production best practice is a **dual-representation approach**:

- **For retrieval** (finding the right table): Generate a natural language summary or description and embed that. Optionally combine the summary with the Markdown/HTML table as a composite chunk. Apply Anthropic-style contextual retrieval to add document context.
- **For LLM consumption** (answering from the table): Store the original structured format (HTML or Markdown) as metadata and pass it to the generation model, which handles structured formats well.
- **For cell-precise queries** (exact values in financial data): Route to SQL-based lookup rather than vector search. The TableRAG framework separates text retrieval from tabular querying via SQL.
- **For large tables**: Keep tables as atomic units when possible. If splitting is necessary, repeat headers in each chunk. Alternatively, load into a database for programmatic querying.

## Metadata preservation and the contextual retrieval breakthrough

Production systems store metadata at two levels. **Structured metadata** (source file, page number, section title, date, file type) is stored as filterable fields in the vector database, enabling pre-filtering before similarity search. All major vector databases—Pinecone, Weaviate, Qdrant, Chroma—support this pattern with varying sophistication. **Contextual metadata** is embedded directly into the chunk text before vectorization.

**Anthropic's contextual retrieval** (September 2024) is the most impactful technique in this space. For each chunk, Claude generates a 50–100 token context explanation using the whole document, which is prepended to the chunk before embedding. The prompt template passes the entire document and the target chunk, asking for "a short succinct context to situate this chunk within the overall document." A chunk reading "The company's revenue grew by 3%" becomes "This chunk is from an SEC filing on ACME corp's performance in Q2 2023; the previous quarter's revenue was $314 million. The company's revenue grew by 3%." Results: **35% reduction** in retrieval failures with contextual embeddings alone, **49%** combined with contextual BM25, and **67%** with added reranking. Cost is ~$1.02 per million document tokens using Claude Haiku with prompt caching.

LlamaIndex includes metadata in embedding text by default through a configurable text template (`{metadata_str}\n\n{content}`), with options to exclude specific keys. LangChain propagates metadata from parent documents to chunks but does not embed metadata into text by default—that requires explicit implementation. Microsoft Azure's architecture guide recommends a **dual-storage pattern**: maintain both a raw chunk (returned to the user) and a cleaned/enriched chunk (vectorized), plus separate metadata fields for title, summary, keywords, and generated questions.

## Text cleaning: less is more for modern embeddings

The cleaning pipeline should be **minimal and targeted**. Modern transformer-based embedding models are trained on natural language and expect it. The standard production cleaning steps are:

1. **Normalize encoding to UTF-8** — prevents downstream bugs from mixed encodings and mojibake
2. **Apply Unicode NFC normalization** — ensures characters like é use a consistent representation (Go: `golang.org/x/text/unicode/norm`)
3. **Normalize whitespace** — collapse multiple spaces and excessive newlines while preserving paragraph breaks
4. **Remove boilerplate** — page headers, footers, page numbers, repeated disclaimers (Unstructured's element typing makes this easy by filtering element types)
5. **Fix OCR artifacts** — ligatures (ﬁ → fi), encoding errors, garbled characters

Critical practices to **avoid**: do not remove stop words (negations like "not" carry critical meaning for embeddings), do not stem or lemmatize (models expect natural word forms), do not aggressively lowercase (destroys proper noun recognition). Microsoft Azure's guide notes that "not" is a stop word that "holds significant semantic meaning." Multiple sources confirm that over-cleaning degrades embedding quality more than under-cleaning.

For Go specifically, `golang.org/x/text` provides the essential text processing foundation: Unicode normalization, encoding conversion (Shift-JIS, ISO-8859-1, Windows-1252 → UTF-8), and collation. The `prose` library (`github.com/jdkato/prose`) offers tokenization, sentence segmentation, and named-entity extraction in pure Go.

## Practical architecture for a Go library

The Go ecosystem for RAG document preprocessing is functional but narrower than Python's. The most relevant Go libraries include **Raggo** (`github.com/teilomillet/raggo`) for lightweight RAG with PDF parsing and chunking, **LangChainGo** (`github.com/tmc/langchaingo`) for the LangChain pattern, and **UniPDF** (`unidoc.io`) for production-grade PDF text extraction. Weaviate, the vector database, is itself written in Go and has a native client.

A Go preprocessing library should **not** attempt to replicate Python's rich document conversion ecosystem. Instead, it should focus on three layers:

**Layer 1 — Text processing (build this):** UTF-8 normalization, Unicode NFC normalization, whitespace normalization, boilerplate detection/removal, and structure-aware chunking (recursive character splitting with Markdown-aware separators: `\n## `, `\n### `, `\n\n`, `\n`, ` `). These are straightforward to implement in Go and benefit from Go's strong string handling and concurrency.

**Layer 2 — External tool integration (document and wrap):** Provide clear interfaces and documentation for plugging in format converters. For PDFs, recommend calling Docling or Marker via subprocess or API, or using pdftotext (poppler) via `os/exec`. For DOCX, recommend Pandoc. For HTML, implement or wrap Mozilla Readability (Go port exists as go-readability). For structured data, recommend loading into DuckDB/SQLite.

**Layer 3 — Metadata and enrichment (build this):** Chunk metadata attachment, contextual retrieval integration (calling Claude or another LLM to generate chunk context), and vector database metadata formatting. Go's goroutine model excels at the concurrent processing pattern needed for contextual retrieval—generating context for hundreds of chunks in parallel.

The **minimum viable preprocessing** that captures ~80% of retrieval quality: use a decent parser that outputs Markdown (not raw text extraction), normalize encoding and whitespace, chunk with structure-aware splitting at 500–1,000 tokens with 100–200 token overlap, and attach source metadata (filename, page number, chunk position). The single highest-value addition after the MVP is Anthropic's contextual retrieval, which alone reduces retrieval failures by 35%.

## Conclusion

The 2024–2025 RAG preprocessing landscape has consolidated around Markdown as the universal intermediate format, structure-aware chunking as the default strategy, and hybrid retrieval (dense embeddings + BM25 + metadata filtering) as the production architecture. The most important insight is that **preprocessing quality directly determines retrieval quality**—one survey found poor data cleaning was the primary cause of RAG pipeline failures in 42% of unsuccessful implementations. For tables specifically, the field is moving beyond naive linearization toward dual-representation approaches that separate retrieval (natural language summaries) from consumption (structured formats). Anthropic's contextual retrieval remains the single highest-impact technique available, and the direction of the field points toward even richer semantic enrichment of chunks before embedding rather than better embedding models alone. For a Go library, the strategic choice is clear: own the text processing and chunking layers where Go excels, integrate with the mature Python/cloud conversion ecosystem for format handling, and prioritize the contextual enrichment pipeline that delivers the largest quality gains.
